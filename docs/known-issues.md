# Known Issues

Issues found during Phase 12 integration testing but not fixed (per the phase constraints: glue fixes only — no algorithm, model, or result changes).

## KI-01: `TIE_TOLERANCE` binding constraint not documented in api.md

**Severity:** Low  
**Evidence:** Running `SELECT DISTINCT binding_constraint FROM pricing_recommendation` returns `MAX_CHANGE`, `MARGIN`, `PRICE_RANGE`, and `TIE_TOLERANCE`. The `api.md` Phase 10b section only mentions `MAX_CHANGE`, `MARGIN`, `STOCK`, and `NO_FEASIBLE_PRICE` as possible values.  
**Affected products:** P013, P015, P016, P018, P021, P022, P030 (7 of 50).  
**What it means:** `TIE_TOLERANCE` is set when two candidate prices yield revenues within `REVENUE_TIE_TOLERANCE = 0.001` of each other and the tie-break rule (smallest move) was applied. The pricing logic is correct; the documentation is incomplete.  
**Suggested fix:** Add `TIE_TOLERANCE` to the `BindingConstraint` description in `docs/api.md` and to the TypeScript `BindingConstraint` type comment in `frontend/src/app/core/models/api.models.ts`. No code change needed — the frontend already handles it via the `string` fallback type.

## KI-02: NumPy `pd.Timedelta` deprecation warning in `next_week_features.py`

**Severity:** Low (warning only — no functional impact)  
**Evidence:** `pytest` output:
```
DeprecationWarning: The 'generic' unit for NumPy timedelta is deprecated, and will raise
an error in the future. This includes implicit conversion of bare integers.
  d = week_start + pd.Timedelta(days=i)
```
**Location:** `data-pipeline/pricing/next_week_features.py`, line 24.  
**Suggested fix:** Replace `pd.Timedelta(days=i)` with `pd.Timedelta(days=int(i))` or `datetime.timedelta(days=i)`. No model or result change.

**Severity:** Medium

**Suggested fix:** The verify script already handles this gracefully. No change needed. Document in README that cleaned CSVs are regenerated by the pipeline.

## KI-07: Backend `revenue_change_abs` field is computed by the API, not stored in MySQL

**Severity:** Low (by design, but worth noting for viva)  
**Evidence:** `docs/api.md` documents `revenue_change_abs` as a field in `GET /api/pricing/<product_id>`. This field does not exist in the `pricing_recommendation` MySQL table; the backend computes it as `expected_revenue - current_revenue`. Verified by inspecting `backend/routes/pricing.py`.  
**Impact:** If the two stored values are independently rounded before storage, the computed difference may differ from `round(expected_revenue - current_revenue, 2)` by ±0.01. This is cosmetic.  
**Suggested fix:** None required. Add a note to `docs/api.md` that `revenue_change_abs` is derived server-side.

## KI-09: Ground-truth fields appear in ETL cleaning/validation code (known, justified)

**Severity:** Low (finding, not a bug — no application code should change)  
**Evidence:** The Phase 13 ground-truth isolation test
(`data-pipeline/tests/test_phase13_gt_isolation.py`) greps all application
packages (`etl/`, `features/`, `models/`, `segmentation/`, `pricing/`,
`explanations/`, `backend/routes/`, `backend/services/`) for ground-truth
identifiers (`revenue_management_gt`, `true_elasticity`, `true_segment`,
`gt_product_elasticity`, `gt_customer_segment`, `purchase_rate`,
`basket_mean`, `basket_std`).  Three application files legitimately reference
these names and are therefore on the test's `ALLOWED_FILES` allowlist:

- `data-pipeline/etl/cleaning.py` — the synthetic data generator bakes
  `true_elasticity` (product) and `true_segment` / `purchase_rate` /
  `basket_mean` / `basket_std` (customer) into the raw CSVs.  `cleaning.py`
  cleans those raw columns so `load_to_mysql.py` can route them into the
  separate GT database (`revenue_management_gt`).  This is ETL plumbing in
  the GT-routing chain, not application decision logic consuming GT.
- `data-pipeline/etl/validation.py` — ETL data-quality check asserting
  `true_elasticity < 0` on the cleaned product table.
- `data-pipeline/pricing/validate_elasticity.py` — validation hook comparing
  estimated vs. true elasticity via `get_gt_engine()` (the proper GT read
  path).  It is the sibling of the already-allowed `validate_pricing.py` and
  `validate_segmentation.py`, and the existing
  `test_pricing_optimizer.py` already excludes all `validate_*.py` via its
  `startswith("validate_")` convention.

**What it means:** The GT-isolation boundary is "no application DECISION
logic (models / pricing / segmentation / explanations / backend routes &
services) may read ground truth"; the ETL chain that physically moves the
generated GT into the GT database, and the validation hooks that compare
against it, are legitimately allowed.  No model, pricing, segmentation, or
explanation module reads GT.
**Suggested fix:** None.  This is documented behaviour.  The allowlist and
rationale live in `test_phase13_gt_isolation.py`; the test passes.
